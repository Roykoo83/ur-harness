# 참고 · 개인 운영환경 패턴

> **이 폴더는 설치 대상이 아닙니다.**
> 하네스는 여기 적힌 어떤 도구도 요구하지 않습니다. 없어도 전부 동작합니다.
>
> 이 글은 **하네스를 만든 사람의 작업 환경**이 어떻게 구성됐는지 적어 둔 것입니다.
> 자기 환경을 손보고 싶은 분에게 참고가 되라고 남깁니다. 그대로 따라 할 필요는 없습니다.

## 왜 따로 빼 두었나

하네스 본체는 **아무 도구도 전제하지 않는다**는 원칙으로 만들었습니다(설계 원칙 ①).
구성원마다 OS도 쓰는 프로그램도 다르니, 설치를 조건으로 걸면 일부에게는 아예 성립하지 않습니다.

그런데 만든 사람의 환경에는 생산성을 위해 덧붙인 것들이 있었고,
그 흔적이 코드와 스킬에 남아 있었습니다. 그대로 두면 두 가지가 생깁니다.

- 받은 사람이 **없는 도구를 찾다가 막힙니다**
- 「전원 사용 가능」이라는 말이 사실이 아니게 됩니다

그래서 운영 경로에서는 전부 걷어내고, **패턴만** 여기에 남겼습니다.

---

## 패턴 ① — 과제마다 작업창을 하나씩

과제가 여럿이면 터미널 탭이 섞입니다. 어느 창이 어느 과제인지 몰라
엉뚱한 폴더에서 명령을 치는 일이 생깁니다.

**해법**: 과제별로 작업창(워크스페이스)을 만들고, 그 창의 작업 디렉터리를 과제 폴더로 고정합니다.
창 이름이 곧 과제명이 되므로 헷갈릴 일이 없습니다.

```
작업창 "AI바우처"      → cwd = .../10_과제/1_수행중/AI바우처/
작업창 "팁스"          → cwd = .../10_과제/1_수행중/팁스/
```

### 하네스에서 쓰는 법

`works` 스킬의 `open` 은 **설정에 명령이 있을 때만** 그것을 부릅니다.
없으면 열 폴더를 알려 주고 끝납니다 — 기본값을 두지 않았습니다.

```yaml
# config/harness.yaml
workspace:
  open_command: "<내 도구> new-workspace --name {title} --cwd {path}"
```

`{title}` 은 과제명, `{path}` 는 과제 폴더로 치환됩니다.
터미널 멀티플렉서(tmux·zellij 등), 에디터 CLI(`code`·`cursor`), OS 파일 관리자 —
자기가 쓰는 것을 넣으면 됩니다.

| 도구 | 예시 |
|---|---|
| 에디터 CLI | `code {path}` |
| tmux | `tmux new-session -d -s {title} -c {path}` |
| macOS Finder | `open {path}` |
| Windows 탐색기 | `explorer {path}` |

**비워 두는 것이 기본입니다.** 폴더를 직접 여는 것으로 충분합니다.

## 패턴 ② — 조직마다 다른 AI 진입점

한 사람이 여러 조직 일을 하면, 조직마다 정본 위치도 규약도 다릅니다.
매번 설정을 바꿔 끼우면 **어느 조직 설정으로 돌고 있는지 모르는 상태**가 됩니다.

**해법**: 조직별로 설정 폴더를 나누고, 진입점을 따로 둡니다.

```
~/.config/<조직A>/     설정 · 자격증명 · 캐시
~/.config/<조직B>/
```

실행할 때 환경변수로 어느 쪽인지 지정합니다.

```bash
CONFIG_HOME=~/.config/<조직A> <AI 클라이언트>
```

하네스는 이것을 **이미 지원합니다** — 설정을 읽는 순서가 정해져 있고,
환경변수(`URH_*`)가 가장 마지막에 덮습니다. 자세한 것은 `core/lib/config.py` 의 머리말.

> **섞어 두지 않는 것이 핵심입니다.** 한 폴더에 두 조직 설정이 섞이면
> 어느 쪽 정본에 쓰고 있는지 알 수 없게 됩니다.

## 패턴 ③ — 브라우저 로그인 세션을 빌려 쓰기

사내 시스템 중에는 API 토큰을 안 주는 것이 있습니다.
사람이 로그인해서 보는 화면에만 자료가 있는 경우입니다.

**해법**: 이미 로그인된 브라우저 안에서 자바스크립트를 실행해 자료를 받아 옵니다.
새로 로그인할 필요가 없고, 2단계 인증도 통과한 상태 그대로 씁니다.

```
인식은 snapshot · 행동은 표준 액션 · 추출은 eval · 대량 처리는 스크립트
```

구체적인 절차는 같은 폴더의 `브라우저_에이전트_패턴/패턴.md` 에 적어 두었습니다.
브라우저 자동화 도구(Playwright·Puppeteer·실브라우저 제어 CLI 등) 위에서 구현합니다.

### 왜 하네스 본체에 넣지 않았나

이 방식은 **대화형 세션에서만** 성립합니다. 자동 실행에는 브라우저가 없습니다.
그리고 세션이 끊기면 조용히 실패합니다 — 「토큰 설정 완료」가 거짓이 되는 종류입니다.

그래서 하네스의 Confluence 접근은 **API 토큰 한 경로만** 씁니다.
토큰이 없으면 그 자리에서 멈춥니다. 폴백으로 조용히 새지 않습니다.

같은 폴더의 `confluence-browser-sync.py` · `confluence-resolve-links.py` 가
브라우저 방식으로 만든 수집기입니다 — **동작하는 예시로** 남겨 두었습니다.

## 패턴 ④ — 보조 워커에게 검증을 맡기기

혼자 만들고 혼자 검토하면 같은 맹점을 두 번 지나갑니다.
특히 **「내가 만든 가드가 정말 작동하는가」** 는 자기가 보기 어렵습니다.

**해법**: 다른 AI 모델에게 비판적 리뷰를 발주합니다. 역할을 나눕니다.

| 역할 | 하는 일 |
|---|---|
| 총괄 | 판단 · 통합 · 최종 책임 |
| 교차검증 | 비판 · 팩트체크 · 「이 주장의 근거가 무엇인가」 |
| 대량 처리 | 추론이 필요 없는 파싱 · 정리 · 색인 |

발주할 때 지키는 것:

1. 지시문에 **출력 파일 경로를 명시**하고 다른 파일은 고치지 말라고 적는다
2. 원본은 **읽기 전용**임을 명시한다
3. 호출한 사실과 결과 파일을 작업로그에 남긴다 — 그것이 유일한 흔적이다
4. 비용이 드는 반복 발주는 건수를 먼저 기록한다

이 하네스의 코드 주석에 **「교차검증 지적」** 으로 시작하는 줄들이 있습니다.
그것이 이 방식으로 잡힌 것들입니다 — 종료코드 계약의 모순,
폴백이 조용히 남아 있던 문제, 검사 범위가 너무 좁았던 것 등.

> 하네스는 이것을 요구하지 않습니다. 혼자 만들어도 됩니다.
> 다만 **중요한 산출물은 한 번 더 누군가에게 깨지게 해 보는 편**이 쌉니다.

| | 하네스 본체 | 개인 환경 |
|---|---|---|
| 정본 구조와 규약 | ✓ | |
| 자동 서비스 17개 | ✓ | |
| 스킬 4종 | ✓ | |
| 설정 한 곳에서 읽기 | ✓ | |
| 과제별 작업창 | | 취향 |
| 조직별 진입점 분리 | | 취향 (하네스가 지원은 함) |
| 브라우저 세션 빌려 쓰기 | | 취향 |
| 보조 워커 교차검증 | | 취향 |

**왼쪽 없이는 성립하지 않고, 오른쪽 없이는 조금 불편할 뿐입니다.**
